Я изучил информацию возможных вариантов реализации баз данных и принял решение создать векторную базу данных,
key-value хранилище, поддерживающее векторное хранилище. Этот вариант показался мне интересным, поскольку векторный
поиск важнен для ML/DS индустрии при работе с эмбеддингами.

Работа выполняется индивидуально, поэтому я выбрал в качестве языка python, лично для меня это будет полезно, поскольку
я не обладаю богатым опытом в проектировании таких объемных систем, работой с интерфейсами и классами, развертыванием
программных систем.

В реализации используются 2 структуры данных
1) VectorEntry. - класс, объекты которого, будут храниться в БД
    @ id - str поле, хранящее id объекта, по которому его можно найти
    @ vector - np.ndarray, массив numpe чисел, представляющий из себя вектор эмбеддинга, загружаемой в базу единицы данных
    @ data - bytes, двоичный массив чисел, хранящий содержание объекта (текста/картинки, загружаемого в БД)
    @ metadata - Dict, питоновский словарь (хэш-таблица) которая хранит дополнительную информацию об объектах, по которой
        можно реализовать фильтрацию при векторном поиске
2) SearchResult
    @ entry - VectorEntry - сам объект из базы данных, найденный при поиске
    @ similarity - float - число в диапазоне от -1 до 1, отвечающее за косинусное сходство между найденым вектором и
        вектором запроса, по которому можно оценить степень семантической близости двух объектов

Чтобы осуществить поиск по id для InMemory БД мы можем взять Dict и построить БД на его основе.
Поэтому были реализованы интерфейс и класс InMemoryVectorStorage позволяющий, совершать следующие операции.

InMemoryVectorStorage:
1) put(id, vector, data, metada) - собирает из входных данных VectorEntry объект и кладет его в Dict. Ничего не возвращает
2) delete(id) - удаляет объект с переданным id из Dict, возвращает bool. Сообщает True, если удалили. False, если не нашли
3) get_by_id(id) - достает VectorEntry с переданным id или None если такого нет.
4) get_all() - возвращает список всех VectorEntry из Dict
5) size() - возвращает int, количество объектов в Dict
6) clear() - очищает всю информацию из Dict

Для возможности сохранять объекты в БД при перезапуске был реализован интерфейс и класс PicklePersistence.
На данный момент мы указываем путь к файлу, куда сохранить БД. Получается, что сохраняя в разные файлы БД в разных состояниях
можно хранить несколько ее состояний. Это кажется мне полезной функцией, но есть мысль переработать этот подход, чтобы при
использовании нужно было передавать не конкретный путь, а просто номер версии, чтобы пользователь только запрашивал конкретную
версию, но не задумывался о том, где и как хранятся объекты.
Пока что это спорный для меня вопрос.

PicklePersistence:
1) flush(storage, path) - Преобразует все данные InMemoryStorage объекта в массив и сохраняет в виде бинарного файла, с помощью модуля pickle
2) load(storage, path) - Считывает из бинарного файла данные, с помощью модуля pickle, преобразует их в массив, затем добавляет их все в Dict, загружает в InMemoryStorage объект

Описанный выше функционал описывает InMemory KV БД c возможностью версионирования и контролем сохранения данных пользователем,
ожидающий векторную специфику данных.

Далее я реализовал возможность векторного поиска ближайших данных с помощью перебора BruteForce, что не используется
в реальных векторных БД, так как не годится для масштабирования на большое кол-во данных, имея O(n) сложность, напрямую
зависящую от количества данных.
В реальности используются различные поисковые индексы ANN, одним из примеров которого служит графовая HNSW, строящая многоуровневый граф
Моя же BruteForce устроена следующим образом:

BruteForceSearch:
1) get_nearest( query, k, filter)
    @ query - np.ndarray, вектор, который представляет из себя эмбеддинг запроса
    @ k - int, количество ближайших векторов, которые мы хотим получить
    @ filter - Dict | None, словарь с метаданными, по которым мы хотим отфильтровать вектора, по принципу точного совпадения
        значений в метаданных, с значениями в фильтре. (Фильтр по совпадению категорий данных) 

В реализации были использованы доп функции:
1) _cosine_similarity(a: np.ndarray, b: np.ndarray) -> float: Считать косинусное расстояние между векторами
2) _matches_filter(entry: VectorEntry, filter: Optional[Dict[str, Any]]) -> bool: Проверять проходит ли объект заданный фильтр
